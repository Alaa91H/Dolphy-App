# Security policy

Dolphy is a wireless-protocol and hardware-testing toolkit. It intentionally
touches radios, USB, local networks and (optionally) root/Shizuku. That makes
security reports especially valuable, and it also means "the app can talk to my
own devices on my own bench" is expected behaviour rather than a vulnerability.

## Supported versions

| Version | Supported |
|---|---|
| `main` (1.0.x releases) | ✅ |
| Anything older | ❌ — please reproduce on `main` first |

## Reporting a vulnerability

**Do not open a public issue for a security problem.**

Use GitHub's private reporting flow:
<https://github.com/Alaa91H/Dolphy-App/security/advisories/new>

Please include:

- affected version/commit and the device/Android version,
- reproduction steps or a proof-of-concept plugin/script,
- the impact you believe it has (data exposure, code execution, privilege
  escalation, denial of service),
- whether the finding needs root, Shizuku, a malicious plugin, or physical
  proximity.

You can expect an acknowledgement within 5 working days and a status update
after triage. We will credit you in the release notes unless you ask otherwise.

## In scope

- Release signing, upgrade paths and artifact integrity
  (`docs/security/RELEASE_SIGNING.md`).
- Plugin trust: signature verification, URL policy, installation consent, the
  permission model (`docs/security/P0-HARDENING.md`).
- Secret storage and the `AndroidKeyStore` envelope (`core/security`).
- The embedded HTTP server used by the QR/tools screens
  (`LocalRequestPolicy`, LAN-only binding, request caps).
- Privileged operations behind root/Shizuku (`rootd`, `Plugins` bridges).
- WebView surfaces rendering remote or plugin-supplied markup.

## Out of scope

- Attacks that require an already-rooted device or a malicious plugin that the
  user explicitly installed and granted permissions to.
- Traffic generated by the radio-testing features themselves being detected,
  jammed or reported by third parties.
- Denial of service against *other* devices — that is what several modules are
  designed to test, under the user's responsibility.
- Findings that only reproduce with `android:debuggable="true"` builds.

## Hardening already in place

- Release builds require a real keystore; the build fails instead of falling
  back to the debug key.
- Plugin imports accept HTTPS only, refuse redirect downgrades, and verify an
  ECDSA P-256 signature over the canonical source before installation.
- Plugin WebViews run with file/content access disabled, mixed content blocked,
  and navigation restricted to HTTPS.
- Unused dangerous permissions were removed; the remaining ones are requested
  at runtime with an explanation.
- CI runs unit tests, `detekt`, Android lint, a secret scan (gitleaks) and
  dependency updates (Dependabot) on every push and pull request.

See `docs/security/THREAT-MODEL.md` for the full adversary model.
