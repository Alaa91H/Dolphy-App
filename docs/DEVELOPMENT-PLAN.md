# خطة تطوير Dolphy — خارطة طريق شاملة

> تاريخ الإعداد: 2026-11-04
> النطاق: `Dolphy-App` (الإصدار 1.0.0، `versionCode` 30000)
> الافتراض: مشرف واحد إلى اثنين، تطوير على الجهاز/محلياً، بدون تتبّع خارجي إجباري.

---

## 0. ملخص تنفيذي

Dolphy تطبيق Android ناضج وظيفياً (Bluetooth/BLE، IR، NFC، QR، شبكة، طباعة، HID، بث، إضافات Python/JS، Root/Shizuku) لكنه يحمل ثلاث فجوات بنيوية تكبح التوسّع:

1. **ملف واحد ضخم**: `MainActivity.kt` ≈ 6,332 سطراً، يليه `IRRemotesScreen.kt` ≈ 4,004 أسطر.
2. **عزل الإضافات ناقص**: الإضافات تعمل داخل عملية التطبيق بنموذج صلاحيات فقط، وليست sandbox على مستوى النظام.
3. **اختبارات رقيقة**: 43 اختبار وحدة فقط، ولا اختبارات واجهة/أجهزة آلية، مع baseline لـ detekt يضم 1,085 ملاحظة قديمة.

الخطة تنفّذ ست مراحل على ~6 أشهر، تبدأ بقياس الأساس وتثبيت الجودة، ثم تفكيك البنية، ثم الأمان والعزل، فالأداء والحجم، ثم حزمة الميزات، وتنتهي بدورة إصدار ناضجة. كل مرحلة لها مخرجات ومعايير قبول قابلة للتحقق.

| البند | القيمة الحالية |

| Python | Chaquopy 17.2 / Python 3.11 |
| الوحدات | `:app`, `:core:model`, `:core:hal`, `:core:security`, `:rootd`, `:bridge:flipper` |
| حجم Kotlin | 71,289 سطراً |
| أكبر الملفات | `MainActivity` 6,332 / `IRRemotesScreen` 4,004 / `JsPluginSession` 2,919 |

| detekt | baseline = 1,085 ملاحظة قديمة، وأي جديدة تُفشل CI |
| التوزيع | APK عالمي واحد بأربع معماريات (~100MB) |
| اللغات | العربية، الإنجليزية، الروسية |
| البوابات | بناء + اختبارات + detekt + lint + gitleaks + Dependabot |

**نقاط قوة يجب الحفاظ عليها**

- فصل منطق قابل للاختبار في وحدات JVM صغيرة (`core:*`, `rootd`, `bridge`).
- نموذج أمان واضح: توقيع ECDSA للإضافات، HTTPS فقط للاستيراد، `LocalHttpPolicy` لكل طلبات LAN، توقيع إصدار إلزامي.
- CI يعمل فعلاً ويشغّل اختبارات كل الوحدات، وكتالوج إصدارات موحّد.
- توثيق أمني ومعماري موجود مسبقاً (`docs/`).

**الفجوات الأساسية**

1. لا قياسات أداء/استقرار موثّقة (بدء بارد، jank، ذاكرة، حجم مكوّنات APK).
2. `MainActivity` يحتوي التنقل، السمة، الإعدادات، الشاشات، وحالة التطبيق معاً.
3. الإضافات في نفس العملية: خطأ إضافة يمكن أن يُسقط التطبيق، ولا حدود CPU/ذاكرة/وقت.
4. `:rootd` وسيط داخل الذاكرة وليس AIDL daemon.
5. cleartext HTTP مفعّل على مستوى التطبيق (مقيّد بالسياسة برمجياً فقط).
6. غياب اختبارات الانحدار للواجهة والصلاحيات ودورة حياة الإضافات.
7. ثلاث لغات فقط، وغطاء إتاحة (TalkBack/تكبير الخط/تقليل الحركة) غير مُقاس.
8. لا قناة إصدار تجريبية ولا آلية تراجع (rollback) واضحة.

## 2. الرؤية والمبادئ

**الرؤية:** أن يصبح Dolphy المرجع العملي لأدوات بحث البروتوكولات اللاسلكية على أندرويد: آمن افتراضياً، سريع على الأجهزة المتوسطة، قابل للتوسّع بإضافات معزولة وموقّعة، بواجهة عربية أصلية واحترافية.

**المبادئ الحاكمة**

1. **الأمان أولاً**: أي ميزة جديدة تمر عبر نموذج الصلاحيات والتوقيع قبل الدمج.
2. **لا كسر للمستخدمين**: ترحيل تدريجي، أعلام ميزات، والحفاظ على توقيع الحزم وأسماء الملفات عند الإمكان.
3. **قياس قبل التحسين**: لا ادعاء تحسين بلا رقم قبل/بعد.
4. **الخصوصية افتراضياً**: لا تحليلات خارجية؛ أي تشخيص يكون محلياً وبموافقة صريحة.
5. **عربية أصلية وRTL كامل**، مع احترام إعدادات النظام (حجم الخط، تقليل الحركة، الوضع الداكن).
6. **تفكيك تدريجي لا إعادة كتابة**: استخراج ملفات وViewModels مع اختبارات توصيف قبل النقل.

## 4. تفصيل المراحل

### P0 — أساس وقياس (أسبوعان)

**المهام**

- قياس خط الأساس وتوثيقه في `docs/PERFORMANCE-BASELINE.md`:
  - زمن البدء البارد والدافئ (`am start -W` على جهاز حقيقي، 20 تكراراً، p50/p95).
  - استهلاك الذاكرة في الخمول وبعد فتح 5 شاشات.
  - jank عبر `dumpsys gfxinfo` أو Macrobenchmark.
  - تفكيك حجم APK عبر `apkanalyzer` (Kotlin/Java، DEX، res، native، assets، Python).
- توسيع CI:
  - تقرير تغطية Kover/Jacoco لكل وحدة مع رفع artifact.
  - تقرير حجم APK ومقارنته بالـ commit السابق (fail عند زيادة > 3%).
  - `dependency-review` على PRs، وتوليد SBOM (CycloneDX).
- ضبط cleartext: توثيق الاستثناءات، وإضافة اختبار يضمن مرور كل طلبات LAN عبر `LocalHttpPolicy`.
- إضافة سجل تشخيص محلي (حلقة محدودة 2MB) قابل للتصدير يدوياً مع تنقيح الأسرار.
- تثبيت سياسة الإصدار: `nightly` (كل ليلة) و`beta` (كل أسبوعين) و`stable` (شهري).
- مراجعة detekt: خفض الـ baseline بنسبة 10% مع قاعدة "لا زيادة".

**معايير القبول**

- وجود أرقام أساس منشورة، وتقرير CI يعرض التغطية والحجم.
- CI يفشل فعلياً عند تجاوز ميزانية الحجم أو كسر اختبار.
- لا توجد تغييرات سلوكية في التطبيق في هذه المرحلة.

**المخاطر**: ضجيج القياس على أجهزة مختلفة — يُثبَّت جهاز مرجعي واحد في التوثيق.

### P1 — بنية قابلة للتوسّع (4–6 أسابيع)

**الهدف**: تقليص `MainActivity` إلى أقل من 1,500 سطر دون تغيير السلوك.

**المهام**

1. **توصيف قبل التفكيك**: اختبارات Compose UI للرحلات الحرجة (فتح الإعدادات، تغيير اللغة، مركز الأذونات، فتح مدير الإضافات).
2. استخراج بالترتيب:
   - `SettingsScreen` + `SettingsViewModel` (أكبر كتلة UI).
   - `NavigationHost` ومخطط المسارات في ملف مستقل.
   - `ThemeHost` (السِّمة، شريط النظام، حجم الواجهة).
   - شاشات الأقسام الرئيسية إلى حزم `feature/*`.
3. `AppContainer` يدوي خفيف (بدون Hilt) لحقن `PluginManager`, `PermissionStore`, `Preferences`.
4. حذف المسارات الميتة: `AccentColorCarousel`, `NavigationCustomizationSections`, `LiquidGlassBottomNavigation` غير المستخدمة بعد تبسيط الشريط، وأعلام الزجاج السائل المثبّتة على `false`.
5. توحيد التصميم: نقل البطاقات/القوائم/الحوارات المتكررة إلى `DesignSystem.kt` مع Tokens (مسافات، أنصاف أقطار، حركات).
6. هيكلة الإعدادات: مخطط مفاتيح مركزي + ترحيل + بحث داخل الإعدادات.
7. إضافة اختبارات: `PluginAccessPolicy`، `PermissionCenter` (المنطق الخالص)، `SettingsRepository` + ترحيل المفاتيح.

**معايير القبول**

- `MainActivity < 1500` سطر، وكل ملف جديد < 800 سطر.
- لا تغيير في لقطات الشاشة المرجعية (golden tests) أو سلوك التنقل.
- تغطية اختبارات الوحدات ≥ 25% في `:app`، و≥ 60% في `:core:*`.
- detekt baseline ينخفض ≥ 25%.

### P2 — أمان وعزل (6–8 أسابيع)

**المهام**

1. **عزل الإضافات في عملية منفصلة** (الأولوية القصوى تقنياً):
   - خدمة `isolatedProcess="true"` + واجهة Binder/AIDL مصغّرة لتبادل الرسائل والواجهة.
   - حد موارد: وقت تنفيذ، ذاكرة، حجم رسائل، عدد الشاشات.
   - عند الانهيار: إعادة تشغيل الخدمة، تعطيل الإضافة مؤقتاً (quarantine)، وإشعار المستخدم.
   - الإبقاء على `PluginPermissions` كطبقة ثانية داخل العملية المعزولة.
2. **AIDL daemon لـ `:rootd`**: نقل `PrivilegedBroker` إلى خدمة مربوطة، مع مهلة، إلغاء، وسجل تدقيق قابل للعرض في الواجهة.
3. **سجل ثقة المفاتيح**: شاشة إدارة مفاتيح الإضافات الموقّعة، إلغاء (revocation)، وتدوير المفاتيح.
4. **تحصين الإدخال**: fuzzing لمحلل `.dolphyplugin` وDSL، وحدود حجم/عمق، واختبارات رفض.
5. **SBOM + توقيع الإصدار**: نشر SHA-256 وبيانات المصدر، وفحص الاعتماديات أسبوعياً.
6. **مصفوفة صلاحيات**: اختبارات آلية لـ Root/Shizuku/بدون صلاحية، والتأكد من الفشل الآمن.

**معايير القبول**

- انهيار إضافة لا يُسقط عملية التطبيق (يُثبت باختبار أجهزة).
- كل استدعاء Root يمر عبر daemon ويسجّل في audit log.
- 0 حالة وصول LAN لخارج الشبكة المحلية في اختبارات السياسة.
- مراجعة threat model محدّثة في `docs/security/`.

**المخاطر**: كسر توافق واجهات الإضافات — يُنفَّذ خلف علم ميزة مع جسر توافق، واختبار هجرة لمدة إصدار كامل.

### P3 — أداء وحجم (4–6 أسابيع)

**المهام**

- **Baseline Profiles** و`Macrobenchmark` لمسارات: البدء، فتح الإعدادات، فتح مركز الأذونات، تحميل قائمة الإضافات.
- تحسين Compose: نماذج `@Immutable`، `derivedStateOf`، مفاتيح قوائم صحيحة، تقليل إعادة التركيب، تأجيل تحميل الشاشات الثقيلة.
- تقليل assets: مراجعة `Flipper-IRDB` وقواعد IR (ضغط/فهرسة عند الطلب)، وإزالة الأصول غير المستخدمة.
- تقسيم ABI/App Bundle مع خطة ترحيل: إبقاء APK عالمي كخيار، وإصدار AAB للمتاجر، ورفع `versionCode` قبل التغيير.
- LeakCanary في debug، StrictMode، وفحص تسريبات ViewModel/المستمعين.
- ميزانية أداء في CI: حجم APK، زمن بدء (على جهاز مرجعي)، وعدد إطارات jank.

**مستهدفات مبدئية** (تُثبَّت بعد P0)

| المؤشر | الهدف |
|---|---|
| بدء بارد p50 | ≤ 1.2 ثانية على جهاز متوسط |
| jank | < 5% من الإطارات |
| حجم APK للمعمارية | ≤ 60MB |
| ذاكرة خمول | ≤ 300MB |
| زمن تحميل الإضافة p95 | ≤ 300ms |

## 6. الاختبار والجودة

**الهرم**

1. **وحدات (سريعة)**: المنطق الخالص في `core:*` والإضافات والصلاحيات.
2. **تكامل JVM**: المستودعات، الترحيلات، سياسات الشبكة والتوقيع.
3. **Compose UI**: الرحلات الحرجة فقط (بدء، إعدادات، أذونات، إضافة).
4. **أجهزة/آلية**: Root/Shizuku، BLE/IR/NFC على أجهزة حقيقية موثّقة في `docs/security/REAL-DEVICE-TEST.md`.

**بوابات الدمج**

- بناء + اختبارات + detekt + lint + gitleaks (موجودة).
- جديدة: تغطية لا تنخفض، حجم لا يزيد > 3%، مراجعة أمنية لأي تغيير في `plugin/` أو `rootd/` أو `AndroidManifest`.
- أي إصلاح خطأ يرفق اختبار انحدار.

## 7. الأمان والخصوصية

- الالتزام بـ `THREAT-MODEL.md` وتحديثه مع كل سطح هجوم جديد.

- إدارة أسرار التوقيع خارج المستودع (موجود) مع تدوير دوري.
- فحص أمني آلي للاعتماديات وSBOM، ومراجعة بشرية للإضافات الرسمية.

## 10. تعريف الإنجاز (DoD)

أي مهمة لا تُعتبر منتهية إلا بـ:

1. كود يبني (`assembleDebug`) ويمر detekt/lint.
2. اختبارات تغطي المنطق الجديد (أو مبرر موثّق لغيابها).
3. تحديث الوثائق ذات الصلة (`ARCHITECTURE.md`, `CHANGELOG.md`, أو وثيقة الميزة).
4. قياس قبل/بعد لأي عمل أداء أو حجم.
5. مراجعة أمنية إن لمست الإضافات/الجذر/الشبكة.
6. بلا تراجع في مؤشرات KPI أو مبرر موثّق.

## 12. ملحق: أوامر مرجعية

```bash
# اختبارات كل الوحدات
./gradlew :app:testDebugUnitTest :core:model:test :core:hal:test \
  :core:security:test :rootd:test :bridge:flipper:test

# بناء وفحص
./gradlew :app:assembleDebug detekt :app:lintVitalRelease

# قياس البدء (على جهاز موصول)
adb shell am start -W -n com.droid.dolphy/.MainActivity

# تفكيك الحجم
apkanalyzer apk summary app/build/outputs/apk/debug/app-debug.apk
```

على هذا الجهاز (Termux) يُستخدم البناء المحلي مع `aapt2` من الحزمة:

```bash
export ANDROID_HOME="$HOME/android-sdk"
export JAVA_HOME="$PREFIX/lib/jvm/java-21-openjdk"
gradle :app:assembleDebug -Pandroid.aapt2FromMavenOverride="$PREFIX/bin/aapt2"
```
